# 战斗任务与分组防御

战斗不再由 `_ATT`、`_INTE`、`_CA`、`_DIS`、`_T2*` 旗控制。既有旗不再发布进攻需求，原进攻单位和旗小队会返程回收；普通运营、外矿、布局及跨 shard 开房旗功能不受影响。新的战斗任务仅运行在发布控制台所在 shard。

```js
// 自动侦察并选择一体机 / 二人 / 四人队及强化档位。
combatTask("E41N8", "E42N8", {mode: "attack"})
// 驻守不会攻击建筑；没有默认超时，仍受派兵批次与能量上限约束。
combatTask("E41N8", "E41N9", {mode: "hold"})
// 可约束队形、强化与派兵预算；holdTicks 从全队首次抵达目标后计算。
combatTask("E41N8", "E42N8", {
  id: "raid_demo", mode: "attack", formation: "quad", boostTier: 3,
  maxWaves: 3, maxEnergy: 120000, timeoutTicks: 15000
})
combatTasks()                 // 概览：阶段、等待原因、队形、档位、批次、已用孵化能量。
combatTasks("raid_demo")      // 详细任务、敌情、选定身体及撤收原因。
combatTaskCancel("raid_demo") // 立即撤销需求，携货返回并回收。
```

`formation` 支持 `auto/solo/duo/quad`；`boostTier` 支持 `auto/0/1/2/3`。显式指定档位不会偷偷退回另一档；同一队全员完成补药、齐员且无疲劳后才能前进。默认清场后撤收；显式设置 `controllerAttack: true` 可追加玩家控制器压制，`loot: true` 可追加 NPC 战利品搬运。任务 ID 正在使用或仍有返程单位时，不能用同 ID 覆盖。

已经完成准备的队员会实际走到本房开阔集合区，各自占用独立停车位；其余队员继续完成孵化或 boost。集合区避开 Spawn 出口、Storage、Terminal、Lab 等运营建筑、道路及房间出入口，并保留外围通行空间。不同任务的停车区互不占用，旧任务自动补齐 `rally` 配置；新建筑、道路或其他单位挡住位置时重新选点。待命单位保持可被友军推让，不设置交通锁。详细任务可查看 `rally` 和 `rallyRetryAt`；没有可达安全位置时每 10 tick 重试。

`combatTasks()` 及 `combatTasks("任务 ID")` 的 `spawnStatus` 显示本批计划人数、已出生、正在孵化、待出生、待强化、强化失败与已准备人数，同时提供出生能量池、下一名战斗单位成本和当前队首角色。准备阶段的 `reason` 随实际状态更新；Storage 库存不等于 Spawn/Extension 可用出生能量。

战斗任务的 fighter、scout 和 controller 出生优先级为 `3.5`，loot 为 `5.5`（数值越小越先）。战斗编队排在建造、升级、维修、采矿物之前；搬运战利品排在维修之前。Manager、采集、补能、强化搬运及本房防守仍按原优先级执行，普通角色需求不受任务优先级覆盖。可在 `settings/combat.ts` 的 `spawnPriority` 调整。

本房存在有效强化需求时，Lab 暂停反应及其搬运任务，优先完成强化所需的清矿、补矿和补能；包括已批准战斗编队中仍待出生的强化成员。强化完成、取消或失效后恢复生产，保留此前批次的剩余数量。配置中单独留有 `boostMode` 不会让生产永久暂停；强化期间缺药走资源调配与原有等待机制。Lab 强化能量按实际所需部件数补充。

RCL8 Storage 搬运爬仍支持无人可补能时的应急小身体；已有可用搬运爬时，继任者等待完整规划身体。严重不足或临近寿命结束时使用固定接班槽提前补充，旧爬在继任者可以工作前继续填能，接班后卸货回收，避免低能出生的小搬运爬长期拖慢编队组装。

先用共享预约器申请 Observer 下一 tick 视野；没有观察覆盖或预约长期不可用，发布一只 scout 实地侦察。死亡后等待 50 tick 才续派，待出生的同名 scout 需求跨人口刷新保持。情报过期时停止新的派工并重新侦察。安全模式、目标无敌效果存在时等待。自己和白名单玩家的单位、建筑受到保护；进攻目标房的无主道路、Container 等可破坏建筑也纳入清场，途经房间和驻守任务保持原来的单位防御规则。

选型使用活跃部件的真实强化倍率、敌方输出和治疗、塔距离、双方前置 TOUGH 承伤、身体 50 部件限制与房间预算。按身体能量、实验室燃料与可配置的药剂权重比较可行配置，并检查整队与其他已接受任务尚未出生成员的药剂总需求。判断过于危险、减伤后的输出无法有效压过治疗或补给不够时，保留原因并等待；不会承诺任意玩家基地或高等级要塞都能由一支四人队打下。默认每 tick 只核算一个任务，同一次核算复用同配比身体；重试间隔 25 tick。bucket 低于 2000 或本 tick 余量不足 25 CPU 时暂缓规划，候选遍历也限制单次 CPU 并为后续运营保留余量。

一体机共用同一套目标、治疗和走位决策；二人队保持前后协同，四人队在房间内保持 2×2、在出口切换蛇形队列后重新集结。算伤包括附近敌人下一步可达攻击、敌塔与强化减伤。治疗分配追踪剩余需求，并使用本 tick 实际已发的治疗目标判断当前续航；远程群攻与单攻比较净伤害，白名单或中立设施在范围内时避免群攻误伤。一个单位每 tick 只有一组主动作、远程和移动决策，防止治疗或移动覆盖先前意图。阵亡、强化失败或队伍不完整时废弃当前批次、撤回存活成员并重算。减伤取整及伤疗结算顺序核对自[官方引擎处理](https://github.com/screeps/engine/blob/master/src/processor/intents/creeps/tick.js)。

进攻先清除目标房所有敌方 creep，包括无武装搬运爬、工人和 PowerCreep，再清理全部可破坏的非 Wall、非 Rampart 建筑。全队的近战、拆除、远程攻击采用同一阶段；群攻可能打到当前阶段之外的建筑或其他屏障时改用单攻。敌方单位或内部建筑被屏障包围时，沿能到达该目标的路线选择当前必要的屏障，只打开一处通道；已有可用开口后继续内部目标，保留其他墙。四人队的通道须容纳 2×2 队形，必要时只扩到队形所需的宽度。覆盖目标的 Rampart 仍须先处理。Controller、Portal、Keeper Lair 等不可破坏对象不属于清场目标。

玩家和 NPC 进攻默认都在敌方单位及上述建筑清空后确认清场并撤收，残留 Wall、Rampart 不阻止完成；最后的确认 tick 重新读取可见目标房，新增敌人或建筑会重置确认。旧任务自动开启的控制器或搬运阶段也按新规则结束，仍有目标则重新清理。显式 `controllerAttack: true` 时，清场后派 CLAIM 紫球攻击仍归玩家所有的控制器；必须在之后 tick 看到压制或降级计时变化才能完成。执行一次有效控制器攻击后结束任务；持续控制器降级需再次发布任务。无法在 CLAIM 寿命内抵达时记录原因并撤收。[原生攻击控制器处理](https://github.com/screeps/engine/blob/master/src/processor/intents/creeps/attackController.js)

NPC 要塞核心不能被 WORK `dismantle`，选择配置和攻击动作都需使用红球或蓝球处理。显式 `loot: true` 时清场后继续搬运，支持合法 NPC 遗迹、墓碑、掉落资源和宝库容器，优先高价值与将消失资源，按距离及周转量最多派四只原生搬运爬。路线危险时停工或撤退，寿命不足时提前携货返回。连续 500 tick 没有回收进展且无人携货，任务撤收并留下未搬完原因。原生遗迹存留与要塞坍塌期限相关，时限按当前现场对象读取。[原生遗迹生成](https://github.com/screeps/engine/blob/master/src/processor/intents/structures/_destroy.js)

房间防御继续按连通敌人分组发布守卫，分组和守位身份在移动中保持稳定。统一塔决策计算距离、能量、效果、敌方支援治疗、减伤及 Rampart 覆盖，优先用足够的塔击杀，再把剩余塔用于其他目标或治疗；已接受的意图不会被后续修理覆盖。守卫可以在健康、塔支援有效、不会空出受威胁入口且有可走返程通道时，短距离出墙追击；默认最多 3 格、8 tick。

默认活动任务上限 8，攻击任务超时 15000 tick；驻守没有固定超时，可指定 `holdTicks`。两种模式默认都最多 3 批兵、实际身体孵化预算 120000 能量（实验室补药消耗另计），需要长期驻守时可显式提高 `maxWaves/maxEnergy`。起点处于战争或 RCL4 以上储能不足 100000 时优先恢复本房；运营角色仍优先于远征队列。结束、取消、超时或达到上限都会撤销需求，存活单位先保存货物再回收。

配置分别集中在 `src/settings/combat.ts`、`combatDefense.ts`、`combatTactics.ts`。现有 100 tick CPU 窗口新增 `tick:combat`、`combat:intel`、`combat:planning` 与 `combat:squad:solo/duo/quad`；守卫和塔计算分别归入现有角色/房间阶段。后者属于顶层内部，不能相加。优化验证覆盖算伤、动作冲突、路线边缘、编队疲劳、任务续发及退出；完整攻防胜率仍需实际对战验证。

参考本地 Harabi 的 Observer/侦察与战利品任务、Tigga 的强要塞侦察和梯度出兵、63bot 的强化编队与共同目标思路；采用 ecbot 的需求、身体、实验室和 CPU 调度接口，未照搬固定旗模板。
