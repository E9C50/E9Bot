# shard1 出生补能中断恢复

## 现场与原因

2026-10-09 检查正式服 shard1 的 E39N5：RCL6，出生池 550/2150，Storage 有 5045 能量，第二个矿区 Container 有 2000 能量。房间只剩一只 2 WORK、1 CARRY、2 MOVE 的矿工，没有 Filler，Spawn 空闲。CPU 使用约 1.3，Bucket 持续增长，出生中断不是 CPU 超时造成。

非空房等待当前容量下的完整身体符合既定策略；问题在于没有恢复补能链路。旧队列先等矿区搬运工，Storage 配送工排在后面，且提升 Storage 配送的分支要求已经有一组正常采矿、搬运单位。唯一矿工只从原矿采满 50 后远距离送往出生设施，无法利用中央库存。发育房的矿区搬运工优先入库，也不能代替稳定的出生池配送。

现场 Storage 位于 (18,29)，Spawn 位于 (17,27)，两者距离仅 2 格，因此临时使用现有矿工搬运库存可以快速恢复出生。

## 修复

- 无搬运工且有库存的发育房，优先等待完整的 Storage 配送工；使用容量预览选择身体，实际出生仍等待足额能量。
- 计入出生池、Storage 和本地矿工在途能量，搬运库存不会使恢复队首反复切回矿区搬运工。
- 缺可用配送工时，已有可搬运矿工临时从 Storage 取能量补 Spawn/Extension。缺 Storage 能量时使用非控制器区域的 Container，再无库存才回原矿采集。
- 部分载荷继续送达，准备阶段不再把临时搬运单位拉回矿位；运输时允许让路。配送恢复后返回原有采矿岗位。
- 控制器缓存和 Terminal 不参与临时取能。既有 sourceId、健康旧矿工和非空房完整身体策略保留。

## 验证

全量单元测试 2187/2187 通过，TypeScript 检查、本地 bundle 构建与 diff 检查通过。回归覆盖真实 550/2150 状态等待 2100 后生产 42 部件配送工、精确资金的最后 50 能量在途、250 tick 内临时矿工从中央库存补足 2100、部分交付/部分取货、即时库存变化、可让路状态和正常采矿恢复。

成熟房已有配送工的路径不新增库存扫描或身体预览。既有正常采运组合及控制器降级恢复优先级保留。
