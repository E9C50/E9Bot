第一轮优化已上传并回读校验 `7982373deac65ab22232a56e97795ad96e12063413951ff71edeefb89416c3cd`，完整窗口 **83375973–83376072**：分项合计 18.674、harvester 6.265、Portal 发现 0.195；但末阶段覆盖只有 **91/100 tick**，bucket 13–19，控制台实际单 tick 为 26.215、20.419，尚未恢复稳定。期间 repairer 从 8 增至 10、builder 从 1 增至 3、miner 从 3 增至 4，因此不能只按总 CPU 作同规模比较。继续优化实验室队列、采集统计/错峰、市场与成熟建设巡检，并对低 bucket 时的和平高血屏障加厚采用自适应错峰。

这是本次近期稳定性验证，不能代表未来敌情、扩房、更多单位或大量建设时的长期 CPU 保证。低 bucket 时仅对和平成熟房维护减频，关键响应和发展房仍保留；策略参数与采样诊断均已记录在 README。

首次 API 快照（tick 83361475）：CPU 配额 20、已用 22.850、bucket 663；Memory 约 100123 字节，其中 rooms 71547、creeps 19902、Portal 情报 3792 字节。保存了 117 个房间 Memory、11 份蓝图、18 座门、25 个扫描房间和 5 个终端任务。角色 Memory 记录约 68 个，包含 repairer 11、harvester 19、filler 11；这些是持久记录数量，并不保证都为当前存活单位。

第二次快照（tick 83361546）：已用 17.534、bucket 726、Memory 101083 字节。单 tick 数值与 100 tick 均值需要区分，也不能把这次自然下降称为优化收益。

本地回归用访问次数验证 Observer 建筑枚举、维修候选筛选、角色目标选择及终端队列索引减少；实际 CPU 收益需要优化版部署后在相近房间/单位规模下重新取完整窗口。

2026-10-02 随 scout 修复按用户要求上传优化代码后，官服捕获首个完整窗口 83362612–83362711：主阶段均值合计 **17.080 CPU/tick**，`tick:shards` 1.243、`shard:portalDiscovery` 0.910，独立 `tick:memory` 0.975；harvester 1.327、filler 0.999、terminal 0.463。该窗口包含历代 9 个退休 scout 的寻路与回收，`creep:sScout` 平均 1.552；这批单位回收后需要再比较稳定窗口。Portal 发现与 Memory 解析合计约 1.885，不能把解析独立归因本身算作全部优化收益。其他房间模块仍有运行波动。

同一窗口内 scout 任务 generation 保持 27，退休 scout 从 9 个陆续回收到 0，当前 scout 连续穿越 E41N8、E40N8、E40N7、E40N6，没有重复补派。之后上传了存量错误封门和旧前置路线的一次性迁移补丁；最终 `default` 分支 main SHA-256 为 `471e227f74681f7c4a6c16beadf50d28635e65e088aeab509f004642f7362571`，main 与 source map 均回读校验一致。该最终补丁的独立 100 tick 窗口尚未采满，以上数值来自前一次上传的核心修复版。
