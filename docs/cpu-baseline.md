# shard3 CPU 优化前基线

## 再次超时与恢复调度缺口（2026-10-09）

本轮官服 API、控制台均为只读，修改和构建仅在本地，继续只做 Git 提交。诊断时官服 `default/main` 与此前本地构建完全一致，SHA-256 为 `f6f92650dafa3adb4a020c5e4afaf65832778db472ad50665af2816752c01e7d`，不是旧代码漏传造成的本轮问题。

初始 API 快照 tick **83517832**：配额 **20 CPU**，Bucket **0**，已用 **30.829**，Memory 约 **122543 字节**。控制台看到 10 个自有房，普通爬约 67–68 只，无战斗任务。后续完整 100 tick 统计窗口如下；这里“完整”指时间跨度，不代表所有阶段都执行完毕：

| --- | ---: | ---: | ---: | ---: |
| 83517899–83517998 | 18.733 | 89/100 | 8 | 20.232 |
| 83517904–83518003 | 18.489 | 88/100 | 16 | 22.342 |

超时或未运行 tick 会让后续阶段缺测，低于 20 的合计不能说明已经恢复。第二窗实际采到的 tick 中，Factory 规划平均约 **1.301 CPU**，终端约 **0.865**、峰 **6.213**，人口刷新峰 **5.285**；早期冷启动窗口人口阶段曾达到 **15.397**。这些是优化前数据。被动监听和控制台抽查没有收到错误消息，不据此否定缺测与低 Bucket 的事实。

源码发现 `factory: 25` 恢复周期只限制生产动作，RoomController 的配方与库存规划仍每房每 tick 执行；空闲 Factory 同样重复查找商品、压矿配方和前置库存。新增独立 `factoryPlanning: 25` 错峰门禁，在恢复期保留已有批次及资源预留；撤房、Factory 失效或物流建筑丢失仍立即清理，正常 Bucket 保持商品立即抢占压矿。实际生产继续重新核对库存、Lab 预留与矿物保留量。

全局资源平衡原为每 30 tick，必定与每 5 tick 的人口刷新重合。恢复期改为每 150 tick、第 1 相位；Bucket 不足 100 时暂停新批量矿物均衡，执行前按 `min(limit, tickLimit)` 保留 14 CPU，并避开人口刷新 tick。未执行的到期待办保留，后续有余量时再运行。旧发送任务每 tick 继续校核、发货，Boost/Lab 直接调料保持即时；能量支援独立保留 30 tick 周期并错开人口刷新，缺能房不必等矿物均衡恢复。

终端发送不依赖 `terminalAmount`；去掉发送前和成功后的重复刷新，只在发送/失败处理结束后准备下一批，冷却期间仍更新一次。50k 终端能量保留、最大可付整批、收货容量与原生发送费用账本保持一致。

受控本地回归的访问次数：单房恢复期 100 tick 的 Factory 容量/规划扫描从 **100 次降至 4 次**，等待 tick 不读库存且保留批次与预留；完整 100k H 发送的交易费查询从 **5 次降至 3 次**。测试覆盖恢复/正常切换、延期后重试、旧任务及 Boost 继续、低 Bucket 自动能量救援、失效 Factory 及时清理。最终 **2017/2017** 全量回归、类型检查和纯本地构建通过。这些是访问次数收益，尚无本轮修复部署后的官服 CPU 降幅或恢复结论。
